# Known limitations and unresolved Windows checks

- The Windows executable cross-builds on Linux; all actual Windows 11 desktop acceptance is pending. Native MSVC CI passed for commit `5b42b57`; that run predates hold-mode implementation and does not validate this change.
- Toggle and opt-in hold/release activation are implemented with restore cursor mode. Virtual cursor is rejected in configuration. Hold behavior needs the dedicated Windows input checks before being considered accepted.
- No game camera isolation. TinyRadial does not register Raw Input or stop ordinary movement from reaching underlying applications. Exclusive fullscreen overlays and anti-cheat compatibility are unverified.
- A normal process refuses higher-integrity targets and cancels when process metadata cannot be queried. TinyRadial never elevates itself.
- Chords use virtual keys; layouts, app keymaps, current focus, IMEs and active editing tools affect behavior. No OEM/punctuation keys, text typing or multi-chord sequences. Sample REAPER/Blender bindings need checking in the user's actual keymap.
- Toggle uses `RegisterHotKey`; it does not promise full trigger suppression. Hold reserves the chord with that API and uses a keyboard hook to consume the physical primary down/repeats/up. Modifier events pass normally; already-delivered Ctrl/Alt/Shift/Win downs cannot be retracted. Injected keyboard events do not start hold gestures. Reserved/occupied activation keys fail with an error. Validate actual event traffic in InputProbe.
- Foreground validation is conservative: even a dialog replacing the captured window cancels. There is an unavoidable OS race after the last foreground check and before Windows handles injected input; user-mode APIs cannot atomically bind `SendInput` to one HWND. No focus stealing or injection into a newly selected window is attempted.
- Modifiers and action/activation primary keys must be released within two seconds for dispatch. Esc remains hooked during this wait. Otherwise the action cancels silently. Physical keyboard interference during the OS batch is outside TinyRadial's control.
- Toggle removes menu hooks immediately unless matching control/button ups are still owed; that drain lasts at most two seconds. Hold keeps a lightweight keyboard observer while enabled, and after cancellation/disable/mode changes until an owned primary up is consumed. Mouse/control draining remains bounded; movement and unrelated input pass normally. No pointer confinement or capture is requested. All hooks are removed on exit.
- Hold commits on the primary key's release, even if activation modifiers were released first. Release over a submenu cancels rather than executing a descendant; use dwell or click to navigate while holding. A tap released before opening does nothing. Overlapping gestures cancel rather than queue actions. If Windows removes or another hook intercepts the keyboard observer, release delivery can fail; Esc/tray disable/exit remain recovery options where input delivery permits. Actual hook reliability is a Windows acceptance check.
- `SendInput` can fail, including on cleanup. Bounded retry submits remaining owned key-ups and an error reports if that fails. Never claim universal recovery from privilege changes, secure desktop transitions, OS/process crashes or hardware state changes. Physically press/release modifiers and terminate the app if input behaves unexpectedly.
- Menus reposition inward near monitor edges; the original pointer may begin away from the displayed center. Use the visible center to cancel/rearm. Display/settings/DPI/power changes cancel rather than trying to keep a menu active during reconfiguration. Mixed DPI behavior remains a host check.
- ASCII case folding only for executable filenames. Labels support UTF-8. Long labels are clipped to their sectors; prefer short names.
- Configuration is explicitly reloaded through the tray. Startup without a valid config exits with a diagnostic; there is no automatic creation or migration. The portable folder should be writable for error logging; errors still appear in dialogs if writing fails.
- Rendering initialization/device-loss failure cancels and reports an error. Restart after a persistent Direct2D failure; automatic device recreation is deferred until a reproducible host issue justifies it.
- Single instance per interactive Windows session. No autostart installer or automatic updates. The optional InputProbe is a user-launched testing tool, not a resident child process.
